# Part 1 — Requirement Scope and AI Assumptions

**Course:** SE3002 — Software Quality Engineering
**Assignment:** Assignment 01 — Quality Evaluation of AI-Generated Software
**Selected SRS:** "Applying Broadcasting/Multicasting/Secured Communication to agentMom in Multi-Agent Systems" — Software Requirements Specification, Version 1.1, Kansas State University, Spring 2003.
**Project under test:** New agentMom — extends agentMom 1.2 with broadcast, multicast, group membership, and secured (encrypted) communication for a Java-based multi-agent messaging framework.

## Scope Note

agentMom is a communication **framework/library**, not an end-user application — the SRS itself defines no GUI, no CRUD entities, and no explicit Non-Functional Requirements section. Two scope decisions follow directly from this and are treated as material, SRS-independent design decisions:

1. **Demo GUI harness.** A small demonstration application (e.g., a Java Swing/JavaFX app that launches multiple "agent" panels/windows, each exposing controls to send/receive/join/leave/encrypt, with an observable log/status area for success and error feedback) is required to satisfy the assignment's runnable-GUI requirement. This harness is not described anywhere in the SRS.
   **Basis: (b) justified by design decision.**
2. **Non-Functional Requirements.** The SRS has no dedicated NFR section. The 3 NFRs selected below are derived from the **Constraints** stated in SRS §2.4, reframed as evaluable non-functional qualities (reliability, security, portability/environment dependency).

## CRUD Compliance

None of the 7 selected FRs are pure CRUD requirements (0 of 7, well within the "no more than 3" limit). This SRS is inherently behavior/workflow-driven (messaging, membership, encryption, architecture selection) rather than data-entity-driven, so no CRUD-style "Manage X Record" FR was needed or selected.

## Requirement Scope Table

| Req. ID | Type | Requirement (brief) | Why selected / risk | AI assumption | Defence / basis |
|---|---|---|---|---|---|
| 3.2.1.1–3.2.1.4 | FR | **Unicast messaging** — send/receive a message to one specific agent; message must arrive only at the specified address, and in order. | Core baseline capability; establishes correctness of addressing and message ordering. Risk: AI may implement send as fire-and-forget without actually guaranteeing ordered arrival under concurrent sends. | Implementation relies on TCP's own ordering guarantee (a single persistent TCP socket per agent pair) rather than building an application-level sequence-number check. | **(a) SRS-supported** — SRS §2.1.2 explicitly mandates TCP/IP for unicast messages, and TCP inherently guarantees in-order delivery, directly satisfying 3.2.1.4. |
| 3.2.2.3–3.2.2.6 | FR | **Multicast group membership control** — an agent may join/leave a multicast group; it must NOT receive group messages before joining, or after leaving. | Strong business-rule FR (access-control-like behaviour), not CRUD. High risk: race conditions around join/leave timing are easy to implement incorrectly. | AI likely assumes join/leave takes effect immediately and synchronously (no acknowledgement or propagation delay), whereas real multicast group membership (IGMP) can lag behind the leave request. | **(c) unsupported** — SRS states the access rule itself but says nothing about timing/synchronization guarantees; must be tested and disclosed, not hidden. |
| 3.2.2.1, 3.2.2.2, 3.2.2.7–3.2.2.9 | FR | **Multicast messaging & configuration** — send/receive multicast messages; configure time-to-live (TTL); configure multicast address/port; receive from multiple groups simultaneously. | Exercises configuration and multi-group behaviour; good source of boundary tests (e.g., TTL = 0, invalid multicast address). | AI likely assumes a fixed/default TTL and performs only loose validation of address/port (e.g., no explicit check that the address falls within the valid multicast range). | **(c) unsupported** — SRS specifies the capability but not validation strictness; this validation behaviour is an AI-introduced assumption. |
| 3.2.3.1, 3.2.3.2, 3.3.3.3 | FR | **Broadcast messaging** — send/receive a message to all hosts on the same local network. | Simple to demonstrate, but constrained by SRS §2.4.4 (broadcast is often restricted to system administrators on real networks). Risk: the test environment (e.g., localhost/VM) may not reflect real broadcast-domain restrictions. | AI implementation assumes the demo/test machine permits broadcast without checking OS-level permissions. | **(c) unsupported** — this directly contradicts SRS §2.4.4, which warns broadcast may require administrator privilege; assuming unrestricted access is an AI-introduced gap that must be tested and reported as a limitation. |
| 3.2.4.1–3.2.4.6 | FR | **Secure message communication** — encrypt/decrypt both unicast and multicast messages; an agent may choose whether to encrypt; received encrypted messages are decrypted automatically. | Best FR for demonstrating a genuine business rule ("agent decides"); directly testable against SonarQube security findings. | SRS never names an encryption algorithm or key length. AI will pick one (e.g., AES via `javax.crypto`) and a key-management approach, since §2.5.3's "key-distribution agent" is described only at a conceptual level. | **(c) unsupported** — algorithm choice, key length, and key-management mechanism are all AI-introduced; must be defended separately as an explicit design decision once made, or disclosed as unsupported if left implicit. |
| 3.2.5.1, 3.2.5.2 | FR | **Conversation-control architecture** — support both an architecture where the agent directly controls conversations, and one where the agent's components control conversations. | Meaningful architectural/workflow FR: tests whether two genuinely distinct control strategies are supported, not just one hardcoded path. Risk: AI may implement one architecture cleanly and stub/fake the other just enough to satisfy the requirement nominally. | Implementation provides both conversation-control architectures as two genuinely separate code paths (not one degenerate case of the other). | **(a) SRS-supported** — 3.2.5.1 and 3.2.5.2 explicitly require both architectures; code must still be inspected to confirm the assumption holds (see risk column), but the assumption itself follows directly from the SRS text. |
| §2.2.4 (Product Function; not separately numbered in §3.2) | FR | **Communication mode selection** — an agent may choose among unicast, multicast, or broadcast for a given outgoing message. | Ties the other communication FRs together into one user-facing decision/workflow; satisfies the rubric's call for "interaction between features." | Since this requirement is stated only as a Product Function (§2.2) and never operationalized as a numbered §3.2 requirement, the AI-assisted implementation must infer the concrete UI/API shape (e.g., a mode selector) itself. | **(b) justified by design decision** — elevated from a Product Function statement into a testable FR; the concrete UI/API shape is a deliberate design choice, not an SRS mandate. |
| §2.4.1 | NFR | **Reliability** — multicast/broadcast message delivery is best-effort only; a message may be delivered to all specified agents or to none. | Directly testable via a fault-injection-style test (e.g., disconnecting one agent mid-multicast) rather than against a hard numeric metric. | AI will not build in retry/acknowledgement logic, since the SRS explicitly allows best-effort delivery — but may silently swallow delivery failures instead of surfacing them to the sender. | **(c) unsupported** — SRS allows best-effort delivery but does not say failures go unreported to the sender; silent failure handling is an AI-introduced gap, not an SRS claim. |
| §2.4.2 | NFR | **Security** — encryption is provided, but there is no guarantee that others cannot decrypt the message. | SonarQube security hotspots/vulnerabilities are directly relevant here (e.g., flagging a weak algorithm or a hardcoded key). | Actual encryption strength depends entirely on the AI's algorithm/key choice (see FR5), which the SRS does not specify. | **(c) unsupported** — the NFR's limitation is SRS-stated, but the assumption of "how weak/strong" is determined solely by an unverified AI implementation choice. |
| §2.4.3 / §2.4.4 | NFR | **Portability / environment dependency** — multicast requires router/NIC/OS support; broadcast may require administrator privileges depending on the network. | SRS gives no measurable threshold (e.g., no stated percentage of environments that must work) — a good candidate to explicitly report as a limitation rather than invent a pass/fail number. | AI-assisted development and testing will likely validate on only one development machine/network, so "portability" is implicitly assumed rather than actually verified across environments. | **(c) unsupported** — SRS states the dependency exists but gives no verification scope; validating on a single machine/network is a testing-process assumption, not an SRS claim, and must be reported as a limitation rather than fabricated as a pass. |

## Summary of Assumption Basis Distribution

| Basis | Count | Requirements |
|---|---|---|
| (a) Supported by the SRS | 2 | Unicast ordering-via-TCP assumption (§2.1.2), conversation-control architecture separation (3.2.5.1/3.2.5.2) |
| (b) Justified by design decision | 2 | Demo GUI harness (cross-cutting), communication mode selection FR (§2.2.4) |
| (c) Unsupported | 7 | Multicast join/leave timing, multicast config validation strictness, broadcast permission bypass, encryption algorithm/key choice, reliability silent-failure handling, security strength dependency, portability single-environment validation |

No unsupported assumption is hidden — each is stated explicitly above alongside the SRS-supported capability it attaches to, per the assignment's requirement that unsupported assumptions must not be concealed.
